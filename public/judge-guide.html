One shared tab.
Direct BCH paybacks.

TabCash records shared expenses, allocates exact satoshis and reduces the payback list. A connected WizardConnect HD wallet can sign a direct BCH mainnet settlement; keys remain in the wallet.

Local prototype; evidence pending. The Austin tab contains fictional sample expenses. The software does not simulate a successful transaction. Public configuration, hosting, wallet interoperability, real transaction evidence and event participation must be completed and verified by the participant.

A two-minute walkthrough without funds

  1. Show the problem (20 seconds). Open the Austin tab and explain that several group members paid for different expenses. Inspect the total and each person's balance.
  2. Show exact math (30 seconds). Add a tiny fictional expense, such as 0.00000010 BCH, split among three sample people. The remainder is assigned deterministically in satoshis. Explain that recording an expense moves no funds.
  3. Show fewer paybacks (30 seconds). Open Review paybacks. The greedy matching plan clears balances; it does not promise a globally minimal transaction count. Close the dialog without connecting a wallet.
  4. Show portability and boundaries (30 seconds). Export the tab. Imports are local, unsigned expense records. Actual payments require valid recipient addresses, an explicit wallet connection, the mainnet acknowledgment and wallet approval.
  5. Close with evidence (10 seconds). Point to the actual repository and short talk/deck once the participant has configured them. Describe remaining work plainly; do not describe a local build as a hosted or funded demonstration.

Optional participant-authorized live segment

Use a dedicated wallet and a real intended recipient. Add the full bitcoincash: recipient address by clicking the person's name. Connect a compatible WizardConnect HD wallet; fund only the displayed receive address with a small amount of BCH. The app scans the first 20 receive and change addresses, excludes CashToken UTXOs, limits a payment to 546–1,000,000 sats and uses a fixed 1,000 sat miner fee.

Review the exact recipient, amount and change in both app and wallet. Authorize only a payment you intend to make. Retain its actual transaction ID, inspect it independently and record confirmation manually. Broadcast acceptance or one server's confirmation report does not itself update the expense ledger. A saved ID with an interrupted broadcast has an unknown outcome; inspect before retrying.

Hosting handoff

  1. Edit the three public values in submission.js: published Widget Factory talk/deck URL, actual source repository URL, and your mainnet token-enabled EMBER2026 voting address. Supply public data only.
  2. Run npm test, npm run check:submission and npm run package:release. The strict check remains blocked while any required field is missing or invalid. It checks formats locally; independently open each public link and verify address ownership.
  3. Upload only the generated release's site/ contents to the participant's chosen HTTPS static host. The ZIP also contains this handoff and a SHA-256 manifest outside site/. npm run package:preview creates a clearly marked local-review artifact while public fields remain pending.
  4. Serve TabCash at the domain root. Open the hosted URL in a clean browser, check the banner links and voting address, complete the walkthrough, test export/import and check layout/keyboard focus on mobile and desktop.
  5. Check outbound relay/Electrum connectivity and actual wallet interoperability on the hosted origin. The static app has no backend or application secrets. Existing hosting CSP rules must allow its wallet relay and Electrum connections; inspect the browser's network errors.
  6. Record a short clear demonstration and the real transaction/confirmation evidence only after participant authorization. Verify the organizer's roll-call, registration, Telegram confirmation and final submission status. These are participant/account actions and are not performed by release packaging.

The participant chooses the host, creates accounts, publishes files and links, verifies event eligibility and approves any real payment. No page here confirms those actions have occurred. The local preview server is a review tool; publishing requires the hosting steps above.
